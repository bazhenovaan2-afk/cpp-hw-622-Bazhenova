# FizzKat — Система управления парком проката

Консольное приложение на C++17 для учёта и обслуживания транспортных средств, экипировки и зарядных станций.

---
## 0. Использование ИИ

Я использовала DeepSeek как собеседника чтобы задавать вопросы, для консольного цикла в `main.cpp` и генерации этого readme. Весь остальной код написан вручную.

## 1. Как собрать и запустить

Для сборки используется компилятор `g++` со стандартом **C++17**.

> **Примечание:** файлы `Things.cpp` и `Transport.cpp` не участвуют в сборке, так как все методы определены прямо в заголовочных файлах (`inline`).

### Сборка проекта
```bash
g++ -std=c++17 -Wall -Wextra -g main.cpp Inventory.cpp -o fizzkat
```

### Запуск
```bash
./fizzkat
```

### Тестовый сценарий
Запустить демонстрационный сценарий из задания можно следующей командой:

```bash
./fizzkat << 'EOF'
add scooter S-1 ModelX 2.5 8
add bike B-1 City 4
add scooter S-2 brokenX 1.0 9
add helmet H-1 Pro
add dock D-1 Hub 10.0
list
novice
energy
quit
EOF
```

## 2. Схема наследования

В проекте реализовано множественное наследование для классов, которые одновременно являются единицей инвентаря и потребителем энергии.

```text
InventoryItem (Абстрактный базис)
├── Transport (Базовый класс для прокатной техники)
│   ├── Bicycle
│   ├── El_samokat (Множественное наследование) : Transport, EnergyConsumer
│   └── ElectricBike (Креативная часть) : Transport, EnergyConsumer
├── Helmet (Вещь на балансе)
└── Dock (Множественное наследование) : InventoryItem, EnergyConsumer

EnergyConsumer (Абстрактный базис для тех, кто тратит энергию)
```

## 3. Smart-указатели

В проекте задействованы все три типа умных указателей из стандартной библиотеки:

* **`std::unique_ptr`** — используется в шаблонном классе `Registry` (внутри `std::vector<std::unique_ptr<T>> items2`), чтобы парк единолично владел принятыми единицами техники. Сырой `delete` нигде не используется.
* **`std::shared_ptr`** — применяется в `std::map<std::string, std::shared_ptr<ModelSpec>>` для хранения спецификаций моделей, чтобы несколько единиц техники одной модели могли ссылаться на один и тот же объект. Также `shared_ptr` (с пустым деструктором) используется в `sharedItems`, чтобы можно было брать `weak_ptr` от объектов, которыми владеет `unique_ptr`.
* **`std::weak_ptr`** — используется для витрины `focus`. Он позволяет отслеживать объект, не владея им. Если объект удаляется из парка командой `remove`, `weak_ptr` становится `expired`, и `show_focus` корректно выводит статус `expired`, не вызывая падения программы.

## 4. Обработка исключений

Реализована иерархия собственных исключений от базового класса `FleetError` (наследник `std::runtime_error`):

| Класс исключения | Условие возникновения | Описание |
| :--- | :--- | :--- |
| **`InspectionError`** | В имени устройства встречается подстрока `broken` (без учёта регистра) | Бросается в `ServiceCenter::inspect()`, означает провал техосмотра. |
| **`ArgumentError`** | Некорректный ввод пользователя в `main` | Пустой `id`, `score` вне диапазона `1..10`, отрицательная энергия, неизвестная команда или нехватка аргументов. |

Все исключения перехватываются в `main` в блоке `catch (const FleetError& e)`, где выводится сообщение в формате `error: <сообщение>`. При возникновении ошибок состояние парка не изменяется (частичное добавление исключено).

## 5. Шаблоны

Добавлен шаблонный класс `Registry<T, Cap>` (в файле `Registry.hpp`), выступающий в роли контейнера-журнала (хранит до `Cap` элементов). В `main` он инстанцируется как:

```cpp
Registry<InventoryItem, 1000> park;
```

* **Основные методы:** `add`, `size`, `operator[]`, `removeById`, а также перегруженный `operator<<`.
* **Специализация:** реализована явная специализация `Registry<std::string, 0>`, которая работает как заглушка (операция добавления ничего не делает).

## 6. Креативная часть

* **Новый транспорт:** добавлен класс `ElectricBike` (электровелосипед), наследующийся от `Transport` и `EnergyConsumer`. В консольный интерфейс добавлена команда:
  ```text
  add ebike <id> <name> <energy> <score>
  ```
* **Кэширование моделей:** добавлен класс `ModelSpec`. При добавлении самокатов и электровелосипедов данные их моделей кэшируются в `std::shared_ptr<ModelSpec>` в `main.cpp`, что наглядно демонстрирует совместное владение ресурсами.
